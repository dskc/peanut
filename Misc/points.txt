2. What changed with LR?
Moving the target LR from 0.01 to 0.003 increased the mean epoch-3 accuracy by 2.28 pp for Adam, 1.80 pp for warmup100, and 3.52 pp for Peanut. For Peanut the seed-specific increases were +3.17, +4.27, and +3.13 pp. For warmup100 they were +2.07, +1.57, and +1.77 pp. Adam was less uniform: +6.67, -0.10, and +0.27 pp. Thus “all three means improved” is accurate, but “every run improved” is not.

Two exploratory LRs cannot identify the best rate. This evaluation subset was reused across settings; a formal tuned comparison would select settings on validation before evaluating an untouched test set. The current numbers remain valid descriptive observations.

4. What the first 40 logged steps show
Because Peanut aims to damp the beginning of training, an epoch-3 table alone misses the most diagnostic behavior. The notebook recorded the first 40 optimizer steps of every run, including: loss computed before the update, gradient L2 norm on that mini-batch, LR used for the update, and the L2 norm of the actual parameter change. Each norm aggregates model tensors; it is not a per-layer or per-coordinate measurement. The complete 18-run return therefore has 720 early trace rows, not full 282-step traces.

Step 1’s loss uses the initialized weights; step 2’s loss is on the next mini-batch after the first update. The batch order was seed-matched, but this is a training transient, not a same-batch finite-difference or curvature measurement.

The following are three-seed means from those traces:

At LR 0.003, Adam’s first update and second-batch loss were markedly smaller. These observations make the initial update worth examining, but do not establish a Hessian, sharpness, or specific moment-state cause. LR and state differences coexist, and the mean hides seed-specific peaks.

The first-update norm ratios reflect Peanut’s programmed 0.2 multiplier and warmup’s 1/100 initial LR. They check the intended code paths, not a newly discovered mechanism.

5. What should count as “collapse”?
It helps to distinguish at least four outcomes:

Numerical failure: a NaN/Inf loss, a non-finite update, an exception, or an aborted run.
Finite transient: a large early loss or gradient followed by continued optimization.
Low final accuracy: a completed run whose score is unacceptable under a stated task threshold or relative to a matched control.
Unusual seed or late failure: a weak seed or a deterioration that appears only after the short window observed here.
I observed item 2 in Adam at LR 0.01. The 18 runs completed and the logged early quantities were finite; the loop also checked loss finiteness at every training step. That supports a narrow no-numerical-collapse observation over this run budget. It does not define an accuracy threshold, rule out rare seeds, or stress-test later training. The original Fashion-MNIST AdamW “collapse” examples refer to lower accuracies, not to a NaN trace demonstrated here, so I would keep the two meanings distinct.

Reducing Adam’s LR shrank its early spike, but Peanut still led by 7.04 pp in mean accuracy. That challenges a one-LR explanation without ruling out better-tuned Adam settings.

6. What was actually trained
This was a CIFAR-10 subset probe, not a full-dataset benchmark. The torchvision dataset has 50,000 training and 10,000 test RGB images; the notebook sampled 12,000/3,000 without replacement, using fixed generators:

train_ids = torch.randperm(
    len(train), generator=torch.Generator().manual_seed(20261114)
)[:12000]
test_ids = torch.randperm(
    len(test), generator=torch.Generator().manual_seed(20261115)
)[:3000]
The saved indices had no duplicates or out-of-range entries; all runs used the same images. This identifies the trial but does not prove subset representativeness.

Images went through transforms.ToTensor(); there were no random crops, flips, color changes, extra normalization, label smoothing, or other augmentation. The training objective was nn.CrossEntropyLoss(). Evaluation used the ordinary fraction of examples for which argmax(logits) == label, so the denominator was 3,000 predictions per run. The model was an intentionally simple RGB adaptation of a TinyCNN, not a pretrained network:

class TinyCIFAR(nn.Module):
    def __init__(self):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3, 32, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(2),
            nn.Conv2d(32, 64, kernel_size=3, padding=1),
            nn.ReLU(),
            nn.MaxPool2d(2),
        )
        self.classifier = nn.Sequential(
            nn.Flatten(),
            nn.Linear(64 * 8 * 8, 128),
            nn.ReLU(),
            nn.Linear(128, 10),
        )

    def forward(self, x):
        return self.classifier(self.features(x))
There was no batch normalization, dropout, or pretrained component. This is a short-run baseline, not a competitive CIFAR-10 recipe.

Each run took three epochs, batch 128, with a seed-controlled shuffled loader. Retaining the last smaller batch gave 94 updates per epoch, or 282 per run. Evaluation used batch 256 and inference mode. Paired arms started from matched weights and first batches, corroborated by identical first-step loss and gradient norms.

“Same seed” is a meaningful local control, but not a guarantee that a Windows CPU execution and a Colab GPU execution will follow bitwise-identical trajectories. PyTorch’s reproducibility notes explain the limits of reproducibility across releases, platforms, and CPU/GPU settings. The experiment should be reproducible as a procedure, not advertised as having universal floating-point identity.

7. Exactly which optimizer settings were compared?
The three main methods were:

Adam: torch.optim.Adam with lr=target_lr, weight_decay=0, and default betas=(0.9, 0.999) and eps=1e-8.
Adam + warmup100: the same Adam settings, but before each optimizer update, its LR was set to target_lr * min(1.0, step / 100) with step starting at 1. After update 100, the LR stayed constant at the target for the remainder of training.
Peanut v2: the author’s implementation from the supplied peanut-2.0.0.zip snapshot, using the same target LR and weight_decay=0. Its custom first-step rule and moment initialization remained unmodified for the eighteen main LR-sweep runs.
For the LR 0.01 warmup arm, the first three actual LRs were 0.0001, 0.0002, and 0.0003; update 100 and later used 0.01. This is linear warmup for 100 updates with no subsequent decay. It was a simple, explicit baseline, not a tuned schedule and not an assertion that 100 is an optimal warmup duration. A schedule of a different length could change the comparison.

The comparison holds task, data, model, seeds, updates, loss, batch sizes, weight decay, and target LR fixed. Optimizer states and actual update magnitudes deliberately differ. This is a fixed-setting comparison, not a tuned-accuracy contest.

9. What is special in the supplied source?
Your high-level description has two understandable modifications: a 0.2-scaled first parameter update, and a larger initial second-moment estimate, v1 = g1**2 rather than standard Adam’s (1 - beta2) * g1**2. The supplied 2.0.0 optimizer source has one further state detail worth noting if someone eventually wants to ablate components: the first moment is stored as zero after the special update. That is an implementation observation and a potentially deliberate design choice, not a diagnosis of a bug.

In the first-gradient branch, the relevant stored state can be summarized as:

state["step"] = 1
state["m"] = torch.zeros_like(p)
state["v"] = grad.pow(2)
For the parameter update itself, the ordinary Adam first-step formula (zero weight decay, with bias correction) and the special Peanut update are, coordinate by coordinate:

Adam:    delta1 = -lr       * g1 / (abs(g1) + eps)
Peanut:  delta1 = -0.2 * lr * g1 / (abs(g1) + eps)
That explains the measured 0.2 first-update norm ratio when the same first gradient is used. Subsequent steps use the saved moment states and the ordinary-looking Adam recurrences with their step-based bias corrections. Because standard Adam normally carries (1-beta1)*g1 into its first moment, m1=0 is an additional state difference affecting later steps. This is useful to record for a component-by-component ablation, while leaving your two-part description intact as the conceptual summary.

The other large difference is the second moment: with beta2=0.999, initial v1=g1**2 is much larger than the ordinary first update of the variance accumulator for a nonzero g1. That often creates damping in later adaptive updates. But the amount depends on later gradients, coordinate-wise history, bias correction, and the state of each parameter. The first-step parameter scaling, first-moment state, and second-moment state are three distinguishable implementation factors, although the author’s conceptual proposal groups them into two stated changes.

10. A simple one-coordinate calculation, not a CNN measurement
To understand why Peanut is not equivalent to the particular 100-step linear warmup, consider a toy coordinate whose gradient g is constant and nonzero at every step, with weight_decay=0 and eps negligible compared with abs(g). Standard bias-corrected Adam then takes approximately its target-LR magnitude per step. For the supplied Peanut initialization, the ratio of the Peanut update magnitude to the standard Adam constant-gradient update magnitude at t >= 2 is:

r_t = [(1 - beta1**(t-1)) / (1 - beta1**t)]
      * sqrt(1 - beta2**t)

r_1 = 0.2  (separate special first-step branch)
For default beta1=0.9 and beta2=0.999:

Step	Peanut toy ratio	Adam linear-warmup100 ratio
1	0.2000	0.0100
2	0.0235	0.0200
10	0.0938	0.1000
40	0.1977	0.4000
94 (epoch 1 here)	0.2996	0.9400
100	0.3086	1.0000
188 (epoch 2)	0.4141	1.0000
282 (epoch 3)	0.4958	1.0000
In this toy, the Peanut coefficient is not even monotonic from step 1 to step 2: the first update is special and the second is much smaller. The linear warmup, by contrast, reaches full target LR at update 100. A method that begins with lower updates need not be an ordinary warmup schedule, and a single nominal LR does not ensure equal update magnitudes. This is useful design context for the accuracy ranking reversal.

The table does not measure per-coordinate effective LR in the real CNN. Gradients are not constant; inactive coordinates and changing parameter trajectories invalidate the toy’s assumptions. At a coordinate with g1=0 but g2 nonzero, for instance, the first v and m states stay zero and the second-step behavior can be substantially less damped than this constant-gradient illustration. It would be a mistake to assert that every Peanut coordinate remains suppressed by exactly the coefficients in the table.

One optional isolated comparison would keep Peanut’s first parameter update and v1 unchanged while replacing m1=0 with the usual Adam first-moment update. The earlier preliminary probe did include such an m1-state variant at LR 0.01; across its three seeds, it produced a lower mean epoch-3 accuracy than the original Peanut in that test. That is a local observation under one short protocol, not proof that m1=0 is generally optimal or required. It also is not the full two-by-two ablation of the two advertised changes.

This code-level distinction is worth preserving for a future researcher, but it should not crowd out your immediate request to hear whether the optimizer ran on another small dataset and what accuracy it produced. The answer to that question is already in the tables.

11. A small decision tree, not a list of mandatory homework
I would choose any additional experiment according to the specific uncertainty, rather than demand a large benchmark from a small CPU-oriented project:

What question is still open?
|
|-- Does Peanut run on another dataset?
|     The CIFAR-10 result here already answers a small version.
|
|-- Does something crash or become non-finite?
|     Record the first bad step and compare a matched baseline.
|
|-- Is a seed's final accuracy unexpectedly low?
|     Separate a finite run from an abort; check LR and budget.
|
|-- Which advertised modification matters?
|     Use the four-case ablation already proposed in this thread.
|
|-- Is warmup an adequate alternative?
|     Compare specified warmup lengths at matched target LRs.
|
|-- Which method is strongest after tuning?
|     Choose LR on validation; keep final test untouched.
|
|-- Does the pattern persist in longer training?
      Extend epochs before claiming convergence or late stability.
The first branch needs no additional experiment to report what has already been observed. A real NaN/Inf report calls for the first failing step, loss, LR, dtype, and possibly an optimizer-state trace; a low-but-finite accuracy report calls for the matched seed, budget, LR, and baseline. A long-run or tuned-performance claim is a different project from this three-epoch probe. All of these routes can be useful without making any one of them a prerequisite for community feedback.

nootxlm’s reply in this thread has already proposed comparing plain Adam, each of the two advertised Peanut modifications separately, and both together, using matched seeds and several LRs, and reporting the worst tested seed alongside the mean. I agree that this would separate effects more cleanly. I have not run that four-case experiment and would not present the proposal as my own. The two-LR comparison above supplies one reason that checking more than LR 0.01 may matter. The optional m1 control in the source discussion is a separate state-level factor, not a substitute for the suggested factorial design.

The lowest of the three seeds is already in the first table, so that part requires no new computation. If the eventual goal is tuned accuracy, however, a small, equal-budget validation search is more relevant than a moment-state ablation. If the goal is the mechanism, the factorial comparison is more relevant than collecting unrelated datasets. The current fixed-setting observation remains useful under either path.

12. Context from adjacent optimizer research
Your idea touches a recognized question: what should Adam do when its running moments have almost no history? A few primary sources provide useful context, without being independent tests of Peanut:

Kalra and Barkeshli, Why Warmup the Learning Rate? Underlying Mechanisms and Improvements (NeurIPS 2024) studies early optimization and describes gradient-informed initialization of Adam’s variance estimate. The paper is relevant to the intuition behind v1=g1**2, but GI-Adam is not the same implementation as this Peanut source. The paper’s sharper loss-landscape explanations cannot be inferred from my loss and update-norm traces: I did not measure a Hessian or preconditioned sharpness.
Abuduweili and Liu, Revisiting the Initial Steps in Adaptive Gradient Descent Optimization (CPAL 2025) examines nonzero second-moment initializations, including data-dependent variants; the research code provides another implementation reference. This supports exploring initialization as a design axis, not treating that paper’s reported improvements as Peanut results.
Ma and Yarats, On the Adequacy of Untuned Warmup for Adaptive Optimization (AAAI 2021) discusses simple warmup as an alternative to more elaborate early-step remedies. It justifies warmup as a low-cost baseline, but does not establish that my predeclared 100-update schedule is the best length. Their heuristic can suggest quite different schedules.
Liu et al., On the Variance of the Adaptive Learning Rate and Beyond (ICLR 2020) introduces RAdam, another approach to early adaptive-rate behavior; the implementation repository makes comparisons possible. RAdam, linear warmup, GI-Adam, and Peanut should remain distinct methods.
Sivaprasad et al., Optimizer Benchmarking Needs to Account for Hyperparameter Tuning (ICML 2020) is helpful for distinguishing a shared-LR comparison from a comparison after method-specific tuning. On constrained hardware, the search cost is part of the decision. A cheap, explicit fixed-LR test is still valuable when it is described as such.
13. Practical references and an optional AdamW caveat
For implementation details, the official Adam, AdamW, reproducibility, and numerical accuracy documentation is more directly useful than an unlimited list of related optimizers.

If someone specifically revisits the author’s Fashion-MNIST AdamW result, it is worth recording the weight-decay setting: the supplied script constructs AdamW without an explicit weight_decay, whereas Adam and Peanut use zero/default-zero weight decay there. PyTorch documents 0.01 as AdamW’s default. That is a possible configuration difference to control in a future comparison, not evidence that it caused the author’s lower accuracy or that any result should be discarded. In my eighteen-run CIFAR-10 sweep, all three methods explicitly used weight_decay=0; AdamW was not an additional main LR-sweep arm.

The source also has general-purpose optimizer API paths, such as closure handling, that are separate from this question. These CIFAR-10 runs called ordinary optimizer.step() without a closure. I would not turn a compatibility consideration on an unused path into an explanation of the accuracy table.

14. Final boundaries for a future reader
The observations are limited to one small architecture, one CIFAR-10 subset, two target LRs, three seeds, three epochs, one specified warmup, and the provided Peanut v2.0.0 snapshot. They do not estimate rare-seed failure probability, prove an optimizer mechanism, establish convergence or best achievable CIFAR-10 accuracy, or reproduce the author’s Windows CPU setup. The evaluation subset was examined across LRs, so it is not an untouched test set for choosing a best configuration.

The Colab output files were checked for completed runs, finite logged quantities, consistent subset IDs, and agreement with the earlier overlapping runs, but I did not independently rerun the experiment on another machine. All observed finite transients and final accuracies are reported with their scope intact. An accessible public notebook or CSV would make them easier to verify independently.
